# 다른 기기와 이어하기 (폰 ↔ PC 합치기) 설계

- 작성일: 2026-10-28
- 상태: 검토 대기

## 1. 배경과 목표

### 배경

- 앱은 서버 없이 동작하고 데이터는 기기(localStorage)에만 저장된다.
- 지금도 **다른 기기로 옮기기**(설정 → 기기·백업)가 있다.
  - 보내는 쪽: 코드 복사·공유, 백업 파일(.json) 저장
  - 받는 쪽: 코드 붙여넣기, 백업 파일 선택
- QR 코드는 동료 일정 공유용이다. 세션 목록만 담기 때문에 전체 데이터를 옮기는 데는 쓸 수 없다.

### 지금 방식의 문제

1. **가져오기가 전체 덮어쓰기다.** 폰과 PC를 번갈아 쓰면, 다른 쪽에서 그사이 입력한 내용이 사라진다.
2. **영수증 사진이 옮겨지지 않는다.** 사진은 IndexedDB에 따로 저장돼 있어 코드·파일에 들어가지 않는다.
3. **폰에서 PC로 보내기가 불편하다.**
   - 데이터가 많으면 코드가 길어 메신저로 보내기 애매하다.
   - iPhone에서 저장한 파일 위치를 찾기 어렵다.
   - 파일을 옮기는 방법 안내가 없다.
4. **찾기 어렵다.** 설정 안쪽에 있다.

### 목표

- 한 사람이 폰과 PC를 **번갈아** 쓴다. 가져올 때 덮어쓰지 않고 **합친다.**
  - 한쪽에서 추가·수정·삭제한 것이 다른 쪽에 반영된다.
  - 다른 쪽에서만 바꾼 것은 사라지지 않는다.
- 옮기는 경로는 두 가지다.
  - **iPhone ↔ Mac:** AirDrop
  - **삼성폰 ↔ Windows:** 카카오톡 나와의 채팅
  - 둘 다 기기의 공유 창에 파일을 넘기는 같은 방식으로 처리한다.
- 영수증 사진도 함께 옮긴다.

### 하지 않는 것

- 실시간 동기화, 서버·외부 저장소
- 메일·클라우드 드라이브 전용 흐름 (공유 창에서 고르면 되지만, 그 경로를 위한 안내나 화면은 따로 만들지 않음)
- 동료와 데이터 합치기 (지금처럼 일정 공유 QR을 쓴다)
- Android 웹앱으로 공유 창에서 바로 받기 (share target)
- QR로 보내기 (데이터가 너무 큼)
- 항목 안의 칸별 합치기 (지출 한 건은 통째로 비교. 출장 정보만 예외로 칸별)
- 충돌 항목을 하나씩 묻는 화면
- 삭제 기록 정리 (행사 기간 동안 쌓여도 작음)

## 2. 결정 사항 (검토 중 합의)

| 질문 | 결정 |
|---|---|
| 사용 방식 | 번갈아 쓰기 → 가져올 때 합치기 |
| 옮기는 경로 | AirDrop, 카카오톡 (공유 창 + 파일). 텍스트 코드는 예비 수단 |
| 같은 항목을 양쪽에서 고쳤을 때 | 나중에 고친 쪽을 자동으로 남기고, 결과를 안내 |
| 합치는 방식 | **A안**: `Store.save()`에서 변경을 자동 기록 → 항목별 최근 수정 우선 |
| 배포 점검 | `node scripts/test-sync.js`를 배포 점검에 추가 |

### A안을 고른 이유

- **B안(마지막으로 주고받은 사본과 3-way 비교)은 위험하다.** 보낸 파일을 상대가 받지 않았거나 순서가 꼬이면 기준이 어긋나, 상대 기기의 데이터를 삭제로 오판할 수 있다.
- **C안(각 기능에 수정 시각을 직접 기록)은 유지가 어렵다.** 저장 지점 약 50곳을 고쳐야 하고, 하나라도 빠뜨리면 그 기능만 조용히 합쳐지지 않는다.

## 3. 합치는 단위와 기기별 설정

### 3.1 합치는 데이터

상태의 각 키를 아래 단위로 쪼갠다. 단위마다 키 문자열을 붙이고, 그 값은 JSON으로 비교한다.

| 상태 키 | 모양 | 단위 키 | 단위 값 |
|---|---|---|---|
| `favorites` | 세션 id 배열 | `favorites\|<id>` | `true` |
| `daily_plan` | `{날짜: [{session_id, note, …}]}` | `daily_plan\|<날짜>\|<session_id>` | 그 항목 객체 |
| `reservations` | `{session_id: {…}}` | `reservations\|<id>` | 값 |
| `backups` | `{session_id: [id]}` | `backups\|<id>` | 배열 통째 |
| `session_notes` | `{session_id: {…}}` | `session_notes\|<id>` | 값 |
| `expenses` | `[{id, …}]` | `expenses\|<id>` | 항목 객체 |
| `checklist` | `null` 또는 `[{id, item, done}]` | `checklist\|<id>` | 항목 객체 |
| `depart_done` | `{키: 값}` | `depart_done\|<키>` | 값 |
| `fixed_off` | 이벤트 id 배열 | `fixed_off\|<id>` | `true` |
| `fixed_edits` | `{이벤트 id: {…}}` | `fixed_edits\|<id>` | 값 |
| `peers` | `[{id, …}]` | `peers\|<id>` | 항목 객체 |
| `news` | `[{id, …}]` | `news\|<id>` | 항목 객체 |
| `expo_booths` | `[{id, …}]` | `expo_booths\|<id>` | 항목 객체 |
| `trip` | 중첩 객체 | `trip\|<점 경로>` (예: `trip\|hotel.name`) | 칸 값 |
| `profile` | `{nickname, topics, services}` | `profile\|nickname`, `profile\|topics`, `profile\|services` | 값 (목록은 통째) |
| `fx_rate`, `budget_usd` | 숫자 | `fx_rate`, `budget_usd` | 값 |
| 그 밖의 키 (앞으로 추가될 키. `sync`와 3.2의 기기별 키는 제외) | 아무 값 | `<키>` | 값 통째 |

- **준비물 기본 항목:** `checklist`가 `null`이면 기본 항목(`Packing.defaults()`, id `pk0`…`pk9`)이 있는 것으로 본다.
  - 기본 항목이 실제로 만들어지는 순간을 "수정"으로 치지 않기 위해서다.
  - 그러지 않으면, 나중에 연 기기의 기본 항목이 더 늦은 시각을 받는다. 그 결과 다른 기기에서 체크한 내용을 덮게 된다.
  - `sync.js`는 기본값 함수를 설정으로 받는다 (순수 함수 유지).
- **순서 되살리기:**
  - 이 기기에 있던 항목은 원래 순서를 지킨다.
  - 새로 들어온 항목은 가져온 쪽 순서대로 뒤에 붙인다.
  - `daily_plan`은 날짜 안에서 같은 규칙을 따른다.

### 3.2 기기마다 따로 두는 키

합치지 않고 파일에도 넣지 않는다. 덮어쓰기 때도 이 기기 값을 유지한다.

| 키 | 이유 |
|---|---|
| `theme`, `text_scale`, `show_kr_hours` | 화면 설정 (폰·PC 따로) |
| `notify` | 알림 권한이 기기마다 다름 |
| `recent_queries` | 이 기기의 검색 습관 |
| `onboarded`, `install_dismissed` | 기기 상태 |
| `weather_cache` | 다시 받을 수 있음 (지금도 빼고 내보냄) |
| `last_backup_at` | 이 기기의 백업 기록 |
| `sync_local` | 이 기기의 보냄·받음 기록 (아래 4.1) |

## 4. 변경 기록과 합치기 규칙

### 4.1 상태에 추가하는 키

- **`sync`** (합치는 데이터와 함께 파일에 들어감)

  ```js
  sync: {
    stamps: { "<단위 키>": 1761634200000 }, // 마지막 수정 시각(ms)
    tombs:  { "<단위 키>": 1761634200000 }  // 삭제 시각(ms)
  }
  ```

  - 한 단위 키는 `stamps`와 `tombs` 중 한쪽에만 있다.
  - `sync` 자체는 단위로 쪼개지 않는다.

- **`sync_local`** (기기별, 3.2)

  ```js
  sync_local: {
    last_sent_at: null,              // 이 기기 시각: 마지막으로 보낸 때
    last_received_at: null,          // 이 기기 시각: 마지막으로 가져오기를 반영한 때
    last_received_exported_at: null, // 그때 가져온 데이터의 exported_at (보낸 기기 시각)
    last_from: ""                    // 그때 보낸 기기 (예: "iPhone · Safari")
  }
  ```

  이 기기 시각과 보낸 기기 시각을 섞어 비교하지 않으려고 칸을 나눈다.

- **되돌리기 사본:** localStorage의 별도 키 `reinvent2026.undo`에 둔다. 상태에는 넣지 않는다 (6.2).

### 4.2 저장할 때 기록하기

- `Store`는 직전 저장본을 단위로 쪼갠 사본 `prev`(단위 키 → JSON 문자열)를 메모리에 둔다.
- **불러올 때 (`Store.load()`):** `prev`를 불러온 상태로 채운다. 이때는 기록하지 않는다.
- **저장할 때 (`Store.save()`):**

  ```
  cur = Sync.units(state)
  cur에만 있거나 값이 다른 키 k → stamps[k] = now, delete tombs[k]
  prev에만 있는 키 k          → tombs[k] = now,  delete stamps[k]
  prev = cur
  ```

- **합치기·덮어쓰기·되돌리기로 상태를 바꿀 때:**
  - 저장하기 전에 `prev`를 새 상태로 맞춘다. 그래야 가져온 항목에 "방금 수정"이 다시 찍히지 않는다.
  - `stamps`와 `tombs`는 합친 결과를 그대로 쓴다.
- **업데이트 전 데이터:** 기록이 없는 항목은 수정 시각을 `0`으로 본다.

### 4.3 합치기 (`Sync.merge(local, remote, opts)`)

단위 키마다 양쪽의 마지막 기록을 하나씩 정한다.

- 그 단위가 있으면 → `{있음, t: stamps[k] || 0, 값}`
- 삭제 기록이 있으면 → `{삭제, t: tombs[k]}`
- 둘 다 없으면 → 모름

그다음 아래 표대로 고른다.

| 이 기기 | 가져온 쪽 | 고르는 것 |
|---|---|---|
| 모름 | 있음 / 삭제 | 가져온 쪽 |
| 있음 / 삭제 | 모름 | 이 기기 |
| 시각이 다름 | 시각이 다름 | 시각이 더 늦은 쪽 |
| 시각 같음, 값 같음 (또는 둘 다 삭제) | | 이 기기 (변화 없음) |
| 시각 같음 (0), 값 다름 | | 가져온 쪽 (기록 없는 예전 항목 → 가져온 쪽 우선) |
| 시각 같음 (0 아님), 한쪽 있음·한쪽 삭제 | | 삭제 쪽 |
| 시각 같음 (0 아님), 값 다름 | | 값의 JSON 문자열이 큰 쪽 (어느 기기에서 합쳐도 같은 결과) |

- 결과의 단위·`stamps`·`tombs`는 고른 쪽 것을 그대로 쓴다.
- 기기별 키(3.2)는 이 기기 값을 유지한다.
- **결과 성질 (테스트로 확인):**
  - 순서를 바꿔 합쳐도 같은 데이터가 나온다: `merge(A,B)`와 `merge(B,A)`.
    - 예외: 기록이 없는 예전 항목(시각 0)끼리 값이 다른 경우. 이때는 일부러 가져온 쪽을 따른다.
  - 같은 것을 다시 합쳐도 그대로다: `merge(M,M) = M`.
  - 오래된 파일을 나중에 합쳐도 최신 데이터는 사라지지 않는다.
- **첫 합치기:** 업데이트 전 데이터는 모두 `t = 0`이라, 첫 합치기는 양쪽을 합친 결과가 된다.
  - 값이 다르면 가져온 쪽을 따른다.
  - 업데이트 전에 지운 항목은 삭제 기록이 없어 되살아날 수 있다. 미리보기에서 이를 안내한다. 안내는 이 기기의 첫 합치기에만 뜬다(4.4).

### 4.4 미리보기 집계 (`merge`가 함께 돌려줌)

- **기능별 숫자:** 추가 / 변경 / 삭제
  - 추가: 이 기기에 없던 단위가 생김
  - 변경: 양쪽에 있고 가져온 쪽 값으로 바뀜
  - 삭제: 이 기기에 있던 단위가 없어짐
- **`overwritten`:** 가져온 쪽이 이겨서 바뀌는 단위 중, 이 기기 기록 시각이 `sync_local.last_received_at`보다 늦은 것의 수.
  - 즉 지난번에 받은 뒤 이 기기에서 고쳤는데, 다른 기기의 더 늦은 수정에 덮이는 경우다.
  - 양쪽 다 이 기기 시각이라 바로 비교할 수 있다.
  - 한 번도 받은 적이 없으면 기준은 0이다.
- **`legacy`:** 이 기기에서 처음 합칠 때(`sync_local.last_received_at`이 비어 있음), 양쪽 어느 쪽이든 기록 없는 항목이 있으면 true.
  - 처음 합칠 때만 보므로 안내는 기기마다 한 번만 뜬다.
  - 상대 기기가 아직 업데이트 전 데이터를 보내도 두 번째부터는 뜨지 않는다.
- **`stale`:** 가져온 데이터의 `exported_at`이 `sync_local.last_received_exported_at`보다 이르면 true. 같은 보낸 기기 시각끼리 비교한다.
- **`photos`:** 새로 저장될 영수증 사진 수

## 5. 영수증 사진

### 사진 번호

- **바꿀 때 새 번호:** 사진을 바꾸면 새 번호 `rc-<지출 id>-<시각 36진수>`를 붙이고, 저장에 성공한 뒤 예전 사진을 지운다(`js/expenses.js`).
  - 그러면 지출 항목의 `receipt_img`가 바뀌어 4.2에서 수정으로 기록된다.
  - 사진 번호는 한 번 정해지면 내용이 바뀌지 않는다.
- **이미 저장된 사진**(`rc-<지출 id>`)은 번호를 그대로 둔다.

### 보낼 때

- 합친 데이터의 지출이 가리키는 사진만 data URL로 넣는다.
- "사진 포함"을 끄면 넣지 않는다.

### 받을 때

- 합친 결과의 지출이 가리키는데 이 기기에 없는 사진을 저장한다.

### 정리

- 합친 결과 지워진 지출의 사진은 바로 지우지 않는다 (되돌리기 대비).
- **다음 가져오기를 반영할 때**, 반영 직전 상태와 새로 합친 결과 **어느 쪽도 가리키지 않는** 사진을 지운다.
  - 반영 직전 상태가 가리키는 사진: 되돌리기 사본이 쓰므로 남긴다.
  - 합친 결과가 가리키는 사진: 이번에 되살아난 지출의 사진일 수 있으므로 남긴다.

### 텍스트 코드

- 사진을 넣지 않는다. 코드 화면에 "사진은 파일로 보내야 함께 옮겨져요"라고 안내한다.

### 정산 화면 안내 문구

- 지금: "옮기기·백업 파일에는 포함되지 않으니"
- 바꿈: "다른 기기로 보내기 파일에 함께 들어가요"

## 6. 화면

### 6.1 보내기·받기

**설정**

- "📲 기기·백업" 카드를 **"🔄 다른 기기와 이어하기"** 로 바꾸고 설정 맨 위로 올린다.
  - **[📤 보내기] [📥 받기]**
  - 상태 줄: "마지막으로 보냄 10/28 15:30 · 받음 10/28 09:10 (iPhone · Safari)"
  - 되돌릴 수 있을 때: "마지막 가져오기 되돌리기 (10/28 15:31)"
  - **[💾 백업 파일 저장]**: 보내기와 같은 파일을 다운로드만 한다.
- 기존 "다른 기기로 옮기기 / 가져오기" 버튼은 이 카드로 대체한다.

**📤 보내기 시트**

1. "영수증 사진 포함 (12장 · 약 4MB)" 체크 (기본 켬)
2. **[공유하기로 보내기]**
   - 시트를 열 때 파일을 미리 만들어 둔다. 사진을 IndexedDB에서 읽어 data URL로 바꾸는 데 시간이 걸린다. 그 사이 버튼은 "준비 중…"으로 막는다.
   - 클릭할 때는 `navigator.share({ files })`만 바로 부른다. iOS Safari는 클릭 직후에만 공유를 허락해서, 클릭 뒤에 파일을 만들면 공유가 거부된다.
   - `navigator.canShare({ files })`가 거짓이면 다운로드로 대체하고 "다운로드 폴더에 저장했어요. AirDrop·카톡으로 보내세요"를 띄운다.
   - 사용자가 공유를 취소하면(AbortError) 조용히 넘어간다.
   - 공유나 다운로드가 끝나면 `sync_local.last_sent_at`과 `last_backup_at`을 갱신한다.
3. **[파일로 저장]**: 다운로드만 한다.
4. **[텍스트 코드 복사 (사진 제외)]**: 압축 코드를 복사한다 (7.2).
5. 기기별 안내 (`browserEnv()`)
   - iPhone: "공유 창에서 AirDrop → 내 Mac"
   - Android: "공유 창에서 카카오톡 → 나와의 채팅"
   - PC: "저장한 파일을 AirDrop·카톡으로 폰에 보내세요"
6. 파일 이름: `reinvent2026-이어하기-YYYYMMDD-HHMM.json` (기기 현지 시각)

**📥 받기 시트**

- 끌어다 놓기 영역("여기에 파일을 끌어다 놓으세요")과 [파일 선택]
  - 시트가 열려 있는 동안에는 창 아무 데나 놓아도 받는다.
  - `accept=".json,application/json"`
- 폰 안내: "AirDrop·카톡으로 받은 파일은 파일 앱 → 다운로드에 있어요"
- 코드 붙여넣기 칸과 [코드로 가져오기]
- 읽으면 바로 반영하지 않고 미리보기(6.2)로 넘어간다.
- 읽을 수 없는 파일: "re:Invent 앱 파일이 아니에요"
- 지원하지 않는 압축 코드: "이 브라우저에서는 이 코드를 풀 수 없어요. 파일로 보내 주세요"

**온보딩**

- "다른 기기에서 가져오기"는 같은 받기 시트를 연다.
- 반영되면 `onboarded = true`가 되고 홈으로 간다.

### 6.2 미리보기·반영·되돌리기

**미리보기 시트**

- 제목: "📥 iPhone · Safari에서 10/28 15:30에 보낸 데이터"
- 0이 아닌 줄만: "내 일정 +5", "지출 +3 · 변경 1", "세션 메모 삭제 1", "영수증 사진 +4"
- 모두 0이면: "이미 같은 상태예요"
- `overwritten > 0`: "⚠️ 이 기기에서 고친 것 중 N건은 다른 기기에서 나중에 고쳐서 그쪽으로 바뀌어요."
- `stale`: "이전에 보낸 파일이에요. 합쳐도 최신 내용은 그대로 남아요."
- `legacy`: "처음 합칠 때는 예전에 지운 항목이 다시 생길 수 있어요."
- 버튼: **[합치기]** / [덮어쓰기] / [취소]
  - **덮어쓰기:** 합치는 데이터를 가져온 것으로 통째로 바꾼다. `stamps`·`tombs`도 가져온 것을 쓰고, 기기별 키는 이 기기 값을 유지한다.
  - 누르면 한 번 더 확인한다: "이 기기에만 있는 일정 2개·지출 1건이 사라져요."

**반영**

1. `reinvent2026.undo`에 반영 직전 상태(합치는 데이터 + `sync`)와 시각을 저장한다.
2. 사진을 정리한다. 반영 직전 상태와 합친 결과 어느 쪽도 가리키지 않는 사진만 지운다 (5).
3. 상태를 바꾸고 `prev`를 맞춘 뒤 저장한다 (4.2).
4. 가져온 사진을 저장한다.
5. `sync_local`을 갱신한다.
   - `last_received_at` = 이 기기의 지금 시각
   - `last_received_exported_at` = 가져온 쪽 `exported_at`
   - `last_from` = 보낸 기기
6. 현재 화면을 다시 그리고 "합쳤어요"와 [되돌리기]를 알린다.

**되돌리기**

- 사본의 합치는 데이터와 `sync`를 되살린다. 기기별 키는 그대로 둔다.
- `prev`를 맞춘 뒤 저장하고, 사본을 지운다.
- 되살린 상태가 가리키는 사진은 정리 전에 남아 있으므로 함께 돌아온다.

## 7. 파일·코드 형식

### 7.1 파일 (.json)

```json
{
  "app": "reinvent2026",
  "kind": "sync",
  "v": 2,
  "exported_at": 1761634200000,
  "from": "iPhone · Safari",
  "data": { "favorites": [], "daily_plan": {}, "…": "합치는 키만", "sync": { "stamps": {}, "tombs": {} } },
  "receipts": { "rc-ex1761…": "data:image/jpeg;base64,…" }
}
```

**읽기 규칙**

- `app === "reinvent2026"`이면 v2 형식이다.
- `profile`이 있는 객체면 예전 백업이다.
  - 상태 통째로 보되, 기기별 키(3.2)는 무시한다.
  - `sync`가 없으니 `legacy`로 처리한다.
  - `exported_at`이 없으니 `stale` 판단에서 뺀다.
- 둘 다 아니면 오류다.

### 7.2 텍스트 코드

| 형식 | 내용 |
|---|---|
| `z1.` + base64url | `gzip(JSON({ v: 2, exported_at, from, data }))`. `CompressionStream("gzip")` 사용 |
| `j1.` + base64url | 압축 없음. `CompressionStream`이 없는 브라우저용 |
| 접두사 없음 | 예전 코드: 상태 통째, base64url |

## 9. 테스트

### 9.1 단위 테스트 (`scripts/test-sync.js`, 배포 점검에 포함)

**기록**

- 바꾼 단위에만 시각이 찍힌다.
- 지우면 삭제 기록이 남는다.
- 다시 만들면 삭제 기록이 없어진다.
- 합친 뒤 저장해도 다시 찍히지 않는다.
- 기본 준비물이 만들어져도 찍히지 않는다.

**합치기**

- 양쪽에서 각자 추가하면 둘 다 남는다.
- 같은 지출을 양쪽에서 고치면 나중 것이 남고, `overwritten`이 맞게 세어진다.
- 삭제가 나중이면 지우고, 수정이 나중이면 남긴다.
- 출장 정보는 칸별로 합쳐진다.
- 기기별 키는 유지된다.
- 순서가 유지된다 (기존 순서 + 새 항목은 뒤에).

**결과 성질**

- `merge(A,B)`와 `merge(B,A)`의 데이터가 같다. 기록이 있는 항목끼리 시각이 같은 경우도 포함하고, 예전 항목 예외(4.3)는 빼고 확인한다.
- `merge(M,M)`은 변경이 0이다.
- 오래된 파일을 나중에 합쳐도 최신 데이터가 유지된다.

**예전 데이터·형식**

- 예전 데이터끼리 합치면 합집합이 되고 가져온 쪽을 우선하며, `legacy`가 표시된다.
- `z1`·`j1`·접두사 없는 예전 코드를 모두 읽는다.
- 예전 백업 파일을 읽는다.

### 9.2 브라우저 테스트 (Playwright, 작업할 때 실행)

- **폰 → PC:**
  - 폰 창(iPhone UA)에서 일정·지출·사진을 넣고 보낸다. `navigator.share`를 가로채 파일을 받는다.
  - PC 창에서 끌어다 놓기와 파일 선택으로 받고, 미리보기 숫자를 확인한 뒤 합친다.
  - 일정·지출·사진이 보여야 한다.
- **PC → 폰:** PC에서 고치고 지운 것을 다시 보내 폰에 반영되는지 본다.
- **되돌리기, 덮어쓰기**(사라질 항목 안내), **텍스트 코드**(사진 제외)
- **기존 테스트:** 설치 화면, 넓은 화면, 이동 시간, re:Play

### 9.3 실기기 확인 (배포 후 사용자)

- iPhone → AirDrop → Mac
- 삼성폰 → 카카오톡 나와의 채팅 → Windows PC
- iPhone 홈 화면 앱에서 [파일 선택]으로 받기

## 10. 위험과 대응

| 위험 | 대응 |
|---|---|
| 기기 시계가 크게 틀림 | 대부분 자동 시간. 미리보기 `overwritten` 안내와 되돌리기로 복구 가능 |
| iOS가 클릭 뒤 늦게 부른 공유를 거부 | 파일을 미리 만들고, 클릭할 때는 `share()`만 호출 |
| 사진이 많아 파일이 큼 | "사진 포함" 끄기. 20장이면 약 8MB로 AirDrop·카톡 모두 가능 |
| 첫 합치기에서 지운 항목이 되살아남 | 미리보기 `legacy` 안내. 업데이트 후부터는 정확 |
| 예전 앱 버전이 새 파일을 못 읽음 | 서비스 워커 업데이트로 양쪽 모두 새 버전이 됨. 예전 코드·파일은 새 버전이 읽음 |
| localStorage 용량 | 되돌리기 사본이 상태 크기만큼 추가됨 (수십~수백 KB). 저장 실패 시 기존 "저장 공간이 부족합니다" 알림 |
